# DECISIONS — lavss monitor (ADR)

Файл содержит реестр архитектурных решений (Architecture Decision Records), **утверждённых в рамках Project Kickoff и Stage 2**.

---

## ADR-001: Создание самостоятельного продукта без зависимости от Grafana / Heartbeat
* **Контекст:** Grafana и Heartbeat присутствуют в инфраструктуре, но не используются активно.
* **Решение:** `lavss monitor` проектируется как полностью самостоятельный продукт. Не строить архитектуру вокруг Grafana/Heartbeat и не делать их зависимостями Alpha 0.1.

## ADR-002: Утверждённый технологический стек
* **Контекст:** Выбор платформы для быстрого создания надёжного веб-интерфейса и бэкенда.
* **Решение:**
  * Backend: **Laravel 13**
  * Frontend: **React + TypeScript + Inertia.js**
  * UI: **Tailwind CSS + shadcn/ui** (собственная дизайн-система `lavss monitor`)
  * Database: **PostgreSQL**
  * Cache / Queue: **Redis**

## ADR-003: Источники метрик и опрос объектов
* **Контекст:** Сбор показателей ресурсоёмкости и доступности объектов.
* **Решение:**
  * Для Linux VPS: **Node Exporter + Prometheus** (без постоянных SSH-подключений).
  * Для Proxmox: **Proxmox API**.
  * Для сайтов: **HTTP/HTTPS checks**.

## ADR-004: Единый Responsive Web App для Mobile и Desktop
* **Контекст:** Требуется удобный мониторинг с телефона и компьютера.
* **Решение:** Использовать единую кодовую базу React + Tailwind CSS для Desktop, Tablet и Mobile с самого первого дня. Не делать нативныe мобильные приложения на этапе Alpha.

## ADR-005: Единая сущность `MonitoredObject` и связи
* **Контекст:** Мониторинг разных типов ресурсов (VPS, Server, Proxmox, Container, Website, WordPress).
* **Решение:** Все ресурсы представляются моделью `MonitoredObject` с атрибутами `id`, `name`, `type`, `status`, `enabled`, `description`, `tags`, `parent_id`. Поддерживать связи «родитель-потомок» без перегрузки главного экрана.

## ADR-006: Канал уведомлений Telegram
* **Контекст:** Требуется информирование о сбоях.
* **Решение:** В Alpha 0.1 реализовать только **Telegram** канал. При этом архитектуру алертов сделать абстрактной (`Alert` $\rightarrow$ `Notification` $\rightarrow$ `Notification Channel`).

## ADR-007: Аутентификация единственного владельца
* **Контекст:** Доступ к системе на этапе Alpha.
* **Решение:** Только вход (login/password) и защита сессии для одного пользователя (владельца). Не делать регистрацию, роли или multi-tenancy в Alpha 0.1.

## ADR-008: Сетевая изоляция Node Exporter через WireGuard
* **Контекст:** Безопасный сбор метрик с удалённых VPS.
* **Решение:** Node Exporter не открывается в интернет. Связь с Prometheus/lavss monitor идет через туннель WireGuard.

## ADR-009: Размещение Alpha 0.1 на PVE Home
* **Контекст:** Хостинг для первой версии.
* **Решение:** Разместить Alpha 0.1 на домашнем Proxmox (PVE Home) в окружении Ubuntu 24.04 (VM/LXC) с использованием Docker Compose.

## ADR-010: Структура Laravel 13 + Inertia React (Единое монолитное приложение)
* **Контекст:** Связывание Laravel бэкенда и React фронтенда.
* **Решение:** Разместить монолитное приложение Laravel 13 + Inertia.js в корне репозитория, отказавшись от искусственных директорий `backend/` и `frontend/`.

## Открытые вопросы для обсуждения (не зафиксированы как решения)

1. **Периодичность опроса сайтов и Prometheus:** С какой частотой выполнять HTTP-проверки сайтов (например, раз в 60 секунд) и опрос Prometheus API в Alpha 0.1, чтобы балансировать нагрузку?
2. **Форматирование сообщений в Telegram:** Использовать ли сводные алерты (digest) при массовом сбое нескольких сайтов на одном VPS, чтобы не спамить в чат?
